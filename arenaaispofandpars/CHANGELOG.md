# История изменений

Формат: краткий список по версиям. Версии до 0.3.0 в этом файле не описаны —
смотрите историю git.

## Unreleased

### `arena-claude.bat` архивирует чаты всегда

- **В батнике нет опции «не архивировать»**: он передаёт `--archive` и
  выставляет `ARENA_CLAUDE_ARCHIVE=1`, перекрывая старое значение из
  окружения. В шапке и в баннере это написано явно.
- **Флаг архивации едет с каждым запросом** (`WarmConnection.ask_stream(...,
  archive=...)` / `ask_stream(..., archive=...)`), а не только с argv демона:
  тёплый демон, поднятый CLI (там архивация по умолчанию выключена),
  переиспользуется шимом — и всё равно архивирует.
- **Отложенный архив больше не теряется**: если следующий промпт уже ждёт,
  беседа не архивируется сейчас (это задерживало бы ответ), но запоминается по
  id в `_WarmBrowserState.pending_archive_ids` и уходит в архив на следующем
  ходу.
- **Архивация по id беседы** (`archive_conversation(..., conversation_id=...)`,
  `_archive_mark_triggers_js`): нужная строка находится в сайдбаре по ссылке,
  поэтому отложенный чат архивируется, даже когда на экране уже другой.
- Повторные попытки ограничены одним разом на ход, список должников — 16
  записей; неудачная попытка не ломает запрос.

### Стриминг шима: удерживается только нерешённое

- **`stream_window()` вместо `HOLDBACK`/`halted`**: при первом же намёке на
  tool-call (`<tool`, ```` ``` ````) поток текста замирал до конца ответа, и на
  ответах с кодом это выглядело как «пришло всё сразу в конце». Теперь
  задерживается ровно нерешённый хвост — недописанный тег/фенс и префикс
  стоп-последовательности; код-блок ````python` идёт обычным текстом, а
  распознанный вызов больше не попадает в ответ ещё и как JSON-текст
  (`tool_use` и только он). Нерешённый хвост и сканируется, поэтому длинный
  ответ не замедляет стриминг (12 тыс. символов в 3-символьных дельтах —
  ~17 мс на весь гейт).
- **`TCP_NODELAY` на SSE-сервере шима** (`disable_nagle_algorithm`): мелкие
  дельты не ждут подтверждения предыдущего сегмента.
- **Метрики `answer.first_delta_ms` и `answer.chars_per_s`** в
  `arena-api --warm-profile`: видно, сколько времени ушло на ожидание Arena и
  как быстро она генерирует, — то есть сколько осталось на её стороне.

### Запрос больше не «долго отправляется»

- **Пустая подпись сессии совместима с тёплым демоном**:
  `_compatible(..., session="")` переиспользует уже поднятый демон, а не
  перезапускает его. Раньше чередование CLI и шима Claude Code (разные
  подписи) давало холодный старт браузера на каждый запрос. Явно указанный и
  другой источник по-прежнему поднимает свой демон.
- **Архивация не встаёт между турнами tool-loop**: `AutoOptions.archive_if_idle`
  — guard, который `WarmSession` заполняет сам (`self._waiting <= 1`). Если
  следующий промпт уже ждёт, архив пропускается с меткой `archive.skipped`.
- **Видимые тайминги**: `arena-api --claude --verbose` печатает
  `request: N chars, M tools, stream=…` и строку ответа
  `prompt N chars -> open X ms, answer N chars, total Y ms`; те же числа
  лежат в `ArenaEngine.last_timings` (`open_ms`, `first_delta_ms`, `total_ms`,
  `prompt_chars`, `answer_chars`).

### Запуск браузера переживает занятый/битый профиль

Симптом: `BrowserType.launch_persistent_context: Target page, context or browser
has been closed`, в выводе Chrome — сообщение о профиле. Это не ошибка Arena:
Chromium отказался открыть `state/direct_browser_profile` (живой `chrome.exe`
или замки `SingletonLock`/`SingletonCookie` после аварийного завершения).

- **Снятие «мёртвых» замков**: `heal_profile_locks()` читает pid из
  `SingletonLock` (файл на Windows, симлинк на POSIX) и удаляет замок, если
  процесс уже не жив; живой замок не трогается (`profile_is_locked()`).
- **Откат на временный профиль**: если профиль занят живым процессом,
  `BrowserEnvironment` поднимает браузер с одноразовым профилем (сессия и так
  подсеивается из Firefox/`cookies.json`), пишет это в stderr и удаляет
  каталог при закрытии. Транзиентный отказ без замков — один повтор с тем же
  профилем.
- **Внятная ошибка вместо простыни Playwright**: `profile_launch_hint()`
  говорит закрыть окна `chrome.exe`/`msedge.exe`, что замки чистятся
  автоматически и что есть `--fresh-profile`.
- **`--fresh-profile` / `AutoOptions.reset_profile` /
  `ARENA_CLAUDE_FRESH_PROFILE=1`**: удалить профиль перед запуском (один раз за
  процесс), когда он уже неисправим.
- **`arena-api --claude --doctor`**: новый шаг «5. Профиль браузера» — путь,
  число файлов, занят ли профиль живым процессом и какие замки сняты.

### Батник переживает сломанную установку

- **`arena-claude.bat` теперь умеет запускать пакет прямо из клона**: если
  `arena-api.exe` не работает (типичный случай — `ModuleNotFoundError: No module
  named 'arena_api'`: скрипт остался, пакет в том Python удалён), батник
  пробует `py -m arena_api` и `python -m arena_api` с `PYTHONPATH` на каталог
  репозитория. Установка при этом не нужна вовсе.
- **Внятная причина в сообщении**: при неудаче печатается вывод `--version` и
  конкретный совет — «модуль удалён, переустановите: `py -m pip install -e "."`»
  либо «сборка слишком старая: `py -m pip install -U -e ".[auto]"`».
- **`arena-api --version` называет отсутствующие зависимости**:
  `sessions : cannot import arena_api.auto: No module named 'httpx'
  (install the dependencies: pip install -e ".[auto]")`.

### Архив беседы после полного ответа

- **`AutoOptions.archive_after_answer` / `arena-api --archive-after-answer`**:
  после того как ответ разобран целиком, библиотека открывает меню беседы и
  нажимает **Archive** (`role="menuitem"` с иконкой `lucide-archive`).
  Действие одноразовое, выполняется только для запроса без `follow_up` (турну
  продолжения нужен открытый чат) и никогда не валит уже полученный ответ:
  неудача — это фаза `archive.missed` в профиле.
- **Поиск меню устойчив к вёрстке**: кандидаты-триггеры ранжируются (кнопка
  `aria-haspopup="menu"` в активной строке → рядом с ней → в сайдбаре), каждый
  пробуется по очереди настоящим кликом (Radix открывается на `pointerdown`),
  а если меню открылось без пункта «Архив», оно закрывается по `Escape` и
  берётся следующий кандидат. Пункт ищется по тексту (`Archive`, `Архив`,
  `В архив`) с учётом `data-disabled`.
- **Шим архивирует по умолчанию** (`ARENA_CLAUDE_ARCHIVE=1`): Claude Code
  создаёт новую беседу на каждый запрос, иначе сайдбар Arena заполняется.
  Отключается `--no-archive` / `ARENA_CLAUDE_ARCHIVE=0`; флаг уходит в тёплый
  демон как `--archive-after-answer` и в прямой клиент как
  `archive_after_answer`. Баннер и `GET /` показывают настройку.

### Батник больше не висит и не пишет кракозябры

- **`arena-claude.bat` выбирает рабочую сборку.** Раньше он запускал первую
  найденную `arena-api`; если в PATH стояла старая сборка без шима, процесс
  умирал мгновенно, а батник молча ждал 60 секунд. Теперь он проверяет
  `--version` у `arena-api`, `py -m arena_api` и `python -m arena_api` и берёт
  первую, где есть `anthropic shim: yes` и `--session`; если таких нет —
  сразу печатает версию найденной и команду обновления.
- **Мгновенная диагностика падения.** Ожидание `/healthz` (30 с) каждую
  секунду проверяет, жив ли процесс: если шим умер — сразу хвост лога
  (UTF-8, поэтому без кракозябр) и `--doctor`.
- **Только латиница в самом батнике** (плюс `chcp 65001` для вывода Python):
  русские сообщения идут из `arena-api --claude --doctor`, а не из `cmd`.
- **Аргументы шиму передаются массивом** через `Start-Process -ArgumentList`,
  поэтому путь к профилю с пробелами не ломает запуск.
- **Шим сам предупреждает о ненайденной сессии в баннере** (одно чтение файла
  при старте): `session : firefox:work -> НЕ НАЙДЕНА (источник firefox:work) —
  Claude Code получит ошибку; проверьте: arena-api --claude --doctor`.
- **`arena-api --version` показывает и поддержку сессий**
  (`sessions : yes (--session firefox, firefox:<profile>, ...)`), а
  `arena-claude.bat version` печатает это же без запуска шима.

### `arena-claude.bat`, диагностика `--doctor` и устойчивость к чужим именам моделей

- **`arena-claude.bat`** — один файл для Windows: поднимает шим на порту
  (скрыто, лог в `%TEMP%\arena-claude-<port>.log`), ждёт `/healthz` до 60 с,
  выставляет `ANTHROPIC_BASE_URL`/`ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL`,
  запускает `claude %*` и гасит шим на выходе. Порт/модель/сессию/движок
  задают переменные `ARENA_CLAUDE_*`; `arena-claude.bat doctor` — диагностика.
  Если порт уже слушает, второй шим не поднимается и чужой не гасится.
- **`arena-api --claude --doctor`** — проверяет четыре звена по порядку и
  называет первое сломанное: установленный пакет (и умеет ли он `--session`),
  сессию (с `--explain` для той же конфигурации), движок (один реальный запрос
  с таймингом первого фрагмента) и протокол на loopback (JSON, SSE и SSE с
  инструментами — как это видит Claude Code). Код возврата 1 при любой проблеме.
- **Неизвестное имя модели больше не валит запрос**: если Arena отвечает
  «model … not found»/«unknown», шим один раз повторяет запрос моделью Arena по
  умолчанию и пишет об этом в лог (Claude Code присылает свои
  `claude-sonnet-…`). Остальные ошибки не ретраятся.
- **Компактнее блок инструментов**: у Claude Code полтора десятка инструментов,
  описания урезаны до 300 символов, инструкции сжаты в один абзац — экономит
  заметную часть контекста на каждом запросе.

### Firefox по умолчанию и принудительный выбор источника сессии

- **`arena-api --claude` берёт сессию Firefox** (`--session firefox`):
  профиль Firefox, его куки и TLS-отпечаток — то, что библиотека читает лучше
  всего, — так что Claude Code разговаривает с Arena как уже вошедший
  пользователь, без анонимного профиля и лишней капчи. Уточнить профиль можно
  `--session firefox:<profile>`, `--session firefox:<profile-root>`,
  `--profile`, `--profile-root` (и переменными `ARENA_CLAUDE_SESSION`,
  `ARENA_CLAUDE_PROFILE`, `ARENA_CLAUDE_PROFILE_ROOT`). Если Firefox не найден,
  шим честно пишет об этом и один раз пробует обычный поиск вместо падения;
  `--session auto` возвращает лестницу сразу.
- **`AutoOptions.session_source` + `--session SOURCE` в CLI**: `firefox`,
  `firefox:<profile>`, `storage`, `chrome`/`edge`/… или `auto`. Принудительный
  источник пропускает лестницу (явные куки и файл тоже), а его отсутствие —
  это `AuthenticationError` со списком проверенных источников, а не тихий
  откат на другой браузер.
- **Демон помнит свою сессию**: в state-файле появилось поле `session`
  (`--session`, `--profile`, `--profile-root`, `--cookies`, `--storage`),
  и `ensure_daemon` не переиспользует демон, запущенный с другой сессией.
  Старые state-файлы читаются как раньше.
- **`--explain` показывает принудительный источник** строкой
  `session source : firefox (forced, ladder skipped)`.

### Claude Code на моделях Arena: Anthropic-совместимый API

- **`arena-api --version`**: печатает версию, **каталог установленного
  пакета** и наличие шима (`--claude`). Старая сборка отвечает на новый флаг
  «unrecognized arguments», и это неотличимо от ошибки в коде — теперь первый
  вопрос «какая копия пакета ответила» решается одной командой.

`arena-api --claude` (или `arena-claude`) поднимает на loopback-порту
Anthropic Messages API, ответы на который генерирует Arena Direct Chat. С
`ANTHROPIC_BASE_URL` на этот порт оболочка Claude Code работает на моделях
вашей сессии — вместо `api.anthropic.com`.

- **`POST /v1/messages`**: поток (`message_start`, `ping`,
  `content_block_start/delta/stop`, `message_delta`, `message_stop`, `error`)
  и обычный JSON; `system`, история диалога, `stop_sequences`, `usage`.
- **Эмуляция tool use**: `tools` рендерятся в промпт строгим форматом
  `<tool_call>{"name": ..., "arguments": {...}}</tool_call>`, ответ
  разбирается обратно в блоки `tool_use` со `stop_reason: "tool_use"`. Без
  этого Claude Code не может ни читать файлы, ни запускать команды.
  Понимаются также ```json-фенс и «голый» JSON (последний — только с полем
  аргументов, чтобы проза не выполнялась как вызов).
- **Стриминг не деградирует**: текстовые ответы идут дельтами; буферизуется
  только тот ответ, в котором реально начал формироваться вызов — с
  удержанием 64 символов, чтобы `<tool_call>` не утёк в текст по частям.
- **`POST /v1/messages/count_tokens`**, **`GET /v1/models`**,
  **`GET /v1/models/{id}`**, **`/healthz`** и `/` с готовыми переменными для
  Claude Code.
- **Движки**: `warm` (тёплый демон, по умолчанию, с автооткатом на `http`),
  `http` (свой `DirectArenaClient`), `echo` (проводка без сессии).
- **Публичное API не менялось**: всё новое — отдельный подпакет
  `arena_api.compat`, точка входа `--claude` и скрипт `arena-claude`.

### Меньше round-trip'ов при отправке, метрики стрима и `--fast-submit`

По таймлайну из `--warm-profile` видно, что из 13–24 с ответа наши накладные
расходы — только **2.0–2.4 с до первого байта** (отправка ~0.5–0.9 с + сеть/
очередь Arena), а 11–22 с идут **после** первого байта, то есть это генерация.
Этот релиз убирает из отправки лишние round-trip'ы и делает видимым, где
именно время после первого байта.

- **Ускорено (`_submit_prompt_via_composer`):** `composer.click()` заменён на
  `focus()` (никакой проверки actionability и анимации — композеру нужен
  только каретка, `fill()`/`type()` сами проверяют редактируемость; `click()`
  остался фолбэком), убраны mouse-move к композеру и к кнопке, а также
  фиксированная пауза 15 мс после ввода. Вместе это ~150–250 мс на промпт.
- **Ускорено:** указатель «прогрева страницы» (`_gentle_page_warmup`) больше не
  выполняется на переиспользованной тёплой вкладке — только на свежем
  документе.
- **Добавлено (`--fast-submit` / `AutoOptions.fast_submit`):** отправка по
  Enter с автоматическим фолбэком на кнопку Send, если приложение не начало
  запрос за ~200 мс. Экономит ещё ~200–300 мс (не нужны поиск кнопки,
  mouse-move и клик). По умолчанию **выключено**: на части аккаунтов Arena
  после отправки эскалирует невидимую v2, и лишний Enter может дать дубль.
- **Ускорено (эвристическая кнопка Send):** ожидание «клик не сработал»
  раньше было фиксированным (500 мс на каждый промпт, где кнопка найдена
  эвристикой). Теперь это опрос по 25 мс с выходом при первой же заявке на
  отправку — платим полные полсекунды только когда отправки действительно нет.
- **Добавлено (разметка отправки):** в таймлайн добавлены фазы `composer.visible`,
  `composer.focused`, `prompt.filled`, `send.dispatched` — видно, сколько из
  времени «до `submit.start`» ушло на страницу, поиск композера, ввод и клик,
  а сколько уже на сеть и ответ Arena.
- **Добавлено (метрики вместо догадок):** таймлайн теперь несёт числа —
  `answer.chunks`, `answer.chars`, `answer.longest_gap_ms`. По ним видно,
  стрим реально шёл всё время или сервер молчал (очередь) — и `--warm-profile`
  печатает их строкой `metrics:` под каждым запросом.
- **Исправлено (гигиена процессов):** демон-потомок держится за сильную ссылку
  и подчищается (`_reap_spawned`), поэтому `Popen.__del__` больше не срабатывает
  в случайный момент; CLI не поднимает демон, если вызывающий код подменил
  `auto_client`/`probe` (тесты и встраивание остаются герметичными).
- **Исправлено:** `_PENDING_WORK_JS` стал raw-строкой (исчезли
  `DeprecationWarning` про `\s`), весь набор тестов проходит и под `-W error`.

### Тёплый путь без перезагрузки страницы и без искусственных пауз

- **Исправлено (главное):** тёплый демон больше не перезагружает Direct Chat
  на каждом запросе. Раньше любое изменение карты cookie считалось «новыми
  куками» (`state.direct_page_ready = False`), а Arena ротирует
  `arena-auth-prod-v1.*` **на каждом ходе** — значит каждый «тёплый» промпт
  заново платил `page.goto()` и новую подпись v3 (1–3 с). Теперь перезагрузку
  вызывают только действительно новые session-cookie (например, после
  `--login`); ротация JWT и собственные cookie страницы (`_ga`, `sb-*`,
  `sidebar_state`, …) не стоят ничего. Новая функция
  `_cookies_need_reload()`.
- **Убраны паузы в решении капчи (`auth/autosolve.py`):** это была вторая
  половина разрыва «23 с с капчей против 18 с без». Аудио-транскрипт набирался
  по одному символу с паузой 40–85 мс, после чего шла «прослушка» 1.35–1.95 с
  (клип уже скачан и распознан), затем ещё 0.18–0.34 с перед verify; проверка
  токена шла тиками по 0.22 с, а после нажатий — 0.7–1.2 с ожидания. Теперь
  ввод одним вызовом, settle-паузы 30–250 мс, опрос токена каждые 50 мс и
  проверка сразу после клика. Из решения убрано ~4 с чистого ожидания.
- **Ускорено (возврат после капчи):** повторная отправка после пройденного
  челленджа ждала фиксированные 2 с — теперь 0.35 с (столько нужно приложению,
  чтобы отправить свой retry, а не человеку).
- **Ускорено (429):** окно «может быть, это капча, а не лимит» сокращено с 12 с
  до 1.5 с. Челлендж ищется сканом на каждой итерации, поэтому виджет
  обнаруживается за десятки миллисекунд; если его нет, а вкладка простаивает
  (`_page_is_working()`), лимит сообщается сразу, а не через 12 секунд.
- **Ускорено (клик по чекбоксу капчи):** пауза перед кликом 350 мс → 120 мс,
  ожидание после клика 800 мс → 250 мс.
- **Добавлено (`arena-api --warm-profile [N]`):** демон всегда ведёт таймлайн
  последних запросов и отдаёт его по запросу — видно, где именно ушло время
  (запуск браузера, загрузка страницы, отправка, первый байт, решение капчи),
  без перезапуска с переменными окружения. Фазы демона подмешиваются в отчёт
  клиента с префиксом `daemon.`, поэтому `ARENA_PROFILE=1` показывает всю
  цепочку целиком.
- **Добавлено (`tools/bench_cli.py`):** метрика «время до первого токена» из

  нет.

### 429 от Arena — чаще капча, чем лимит: сначала решаем, потом сообщаем

- **Исправлено (браузерный путь Direct Chat):** ответ `429` больше не
  превращается сразу в `RateLimitError`. Arena отвечает так и на неудачную или
  повторно запрошенную reCAPTCHA, причём тело ответа — обычный JSON без
  маркеров челленджа (`{"error":"too many requests"}`), поэтому прежняя
  проверка по телу его не распознавала, `autosolve` не запускался вовсе, и
  пользователь видел «Arena rate limit reached» вместо решения капчи.
  Теперь при доступном решателе (или явно переданном `solver=`) `429`
  считается кандидатом на челлендж: страница сканируется
  (`_detect_post_submit_challenge`), капча кликается/решается, промпт
  отправляется повторно. Настоящий лимит по-прежнему всплывает —
  `RateLimitError` бросается, только если в отведённом окне на странице так и
  не появилось челленджа.
- **Исправлено (`_raise_browser_http_error`):** `429` с явными маркерами
  челленджа (`cf-mitigated: challenge`, страница проверки) теперь относится к
  `403`/`503`, то есть даёт `ChallengeRequiredError` с понятным действием, а не
  «лимит». Для настоящего лимита сообщение называет, что именно проверялось
  («No verification challenge was found on the page (captcha solving: …)») и
  сохраняет `retry_after` из заголовка.
- **Исправлено (скрытый браузер):** если решатель передан явно
  (`solver=`), скан челленджа и ожидание теперь работают и в невидимом окне, а
  не только при `show_browser`; раньше явный решатель в фоне просто не
  вызывался.
- **Улучшено (`tools/bench_cli.py`):** никаких пауз и повторов между прогонами
  — замер идёт подряд, как обычный цикл вызовов CLI. Зато сбой одного прогона
  больше не обрывает весь бенчмарк: он печатает строку `failed` с первой
  строкой ошибки, продолжает мерить вторую половину и печатает коэффициент,
  если измерены обе стороны.

### Тёплый демон: повторные `--prompt` без запуска браузера

- **Ускорено (`arena-api --prompt ...` повторно):** первый вызов поднимает
  фоновый демон `python -m arena_api.warm`, который держит браузер, вкладку
  Direct Chat и сессию уже готовыми. Следующие вызовы CLI подключаются к нему

  `--warm` / `--no-warm`, `--warm-status`, `--warm-stop`, `--warm-idle`,
  `--warm-timeout`, `--warm-state`, `--warm-start` (поднять демон заранее,
  например из скрипта при входе) и переменные `ARENA_WARM`,
  `ARENA_WARM_IDLE`, `ARENA_WARM_TIMEOUT`, `ARENA_WARM_STATE`.
- **Надёжность:** при любой проблеме (нет браузера, занятый профиль,

  idle-таймаута; простаивая 900 с (по умолчанию), он закрывает браузер сам.
- **Ускорено (`import`/старт CLI):** консольная точка входа переехала в новый

  обслуживает прежний `arena_api.auto.main` без изменений.
- **Добавлено (`ARENA_PROFILE=1` / `ARENA_PROFILE=json`):** встроенный
  профилировщик фаз (`arena_api/latency.py`) — поиск сессии, запуск браузера,

  запуска; при выключенном профилировании каждая точка стоит одну проверку
  флага. Помогает понять, где именно теряется время на конкретной машине.
- **Тесты:** `tests/test_warm.py` (протокол демона на настоящих сокетах, права
  state-файла, отказы/таймауты, переиспользование и замена демона,

  `tests/test_latency.py` (метки, `span`, JSON-отчёт, отсутствие тяжёлых
  импортов в лёгком пути).

### Фоновая пред-навигация тёплой вкладки Direct Chat

- **Ускорено (`DirectArenaClient.complete()/stream()` подряд):** сразу после
  завершения одиночного ответа тёплая вкладка в фоне возвращается на страницу
  Direct Chat, пока вызывающий код обрабатывает результат. Следующий запрос
  застаёт страницу уже загруженной и полностью пропускает `page.goto()` на
  критическом пути (−1…2 с на каждый повторный запрос). Ходы `client.chat()`
  не затрагиваются: открытый диалог остаётся открытым, пред-навигация для них
  не запускается. Подсказка передаётся только раннерам с
  `supports_prefetch_hint = True`, сторонние объекты `verification_token`
  получают прежние аргументы.
- **Исправлено (самовосстановление тёплого браузера):** перед повторным
  использованием вкладки выполняется дешёвая проверка `page.title()`; упавший
  или отсоединённый рендерер теперь перезапускается прозрачно и тогда, когда
  навигация не нужна. Legacy-перехватчики `expose_function` (страницы без
  `page.on`) переподключаются к очереди текущего запроса вместо первой.

### Ещё быстрее: ленивый импорт пакета и кэш чтения cookie-хранилища Firefox

- **Ускорено (`import arena_api`, `import arena_api.auth`):** все публичные

  подмодулям (`arena_api.auto`, `arena_api.auth.browser`) работают как раньше;
  тяжёлые модули импортируются при первом обращении.
- **Ускорено (`FirefoxSessionManager.load_cookies()` / `cookie_records()`):**
  результат последнего чтения кэшируется по stat-отпечатку (`mtime_ns`, размер)

  SQLite/rookiepy, пока Firefox ничего не записал на диск; любая запись

### Точный отпечаток Firefox (`User-Agent`, `Accept-Language`, H2-заголовки) и фильтрация пассивного `jsd`-маяка Cloudflare

- **Исправлено (`FirefoxSessionManager.user_agent()`):** начиная с Firefox 120
  Mozilla разморозила `rv:109.0` (`nsHttpHandler.cpp`: `rv:<major>.0` и
  `Firefox/<major>.0` без `.patch`-версии из `compatibility.ini`). Старое
  значение `rv:109.0` и передача `.patch`-номера ломали криптографическую
  привязку `cf_clearance` к `User-Agent`, из-за чего Cloudflare отклонял живую
  сессию Firefox даже с `impersonate="firefox"`. Также добавлено чтение
  `general.useragent.override` из `prefs.js`.
- **Исправлено (`FirefoxSessionManager.accept_language()` на Windows):** в
  Windows `locale.getlocale()` возвращает словесные названия локалей CRT вроде
  `Russian_Russia` или `English_United States` вместо BCP-47 (`ru-RU`, `en-US`),
  что приводило к отправке невалидного заголовка
  `Accept-Language: Russian-Russia,russian;q=0.8,...`. Теперь используется
  Windows UI LCID (`GetUserDefaultUILanguage` -> `locale.windows_locale`),
  `intl.locale.requested` из `prefs.js` и строгая проверка синтаксиса BCP-47.
- **Исправлено (`ArenaTransport` при `impersonate=`):** при работе через
  `curl_cffi` теперь передаются браузерные заголовки транспортного уровня
  (`Accept-Encoding: gzip, deflate, br, zstd`, `Referer` для `same-origin`,
  а для профилей `firefox*` — `Te: trailers` и `Priority: u=4`), вместо
  урезанного `Accept-Encoding: gzip, deflate` от `httpx`.
- **Исправлено (`transport.py`, `auto.py`, `challenge.py`):** пассивный скрипт
  телеметрии Cloudflare `/cdn-cgi/challenge-platform/scripts/jsd/main.js` и
  упоминание `turnstile` в обычных страницах Next.js (`200` и `404` на `/config`)
  больше не принимаются ошибочно за блокирующую капчу `ChallengeRequiredError`.

### Приоритет авторизованного профиля над гостевым `state/cookies.json` и чистое поведение `--status`

- **Исправлено:** незавершённый запуск `--login` мог сохранить в `./state/cookies.json`
  только гостевые и аналитические cookie (`provisional_user_id`, `_ga`, `_dd_s`,
  `cf_clearance`, `sidebar_state`), которые затем затеняли реально авторизованный

  источников (`./state/cookies.json` по умолчанию и профили браузеров)
  авторизованная сессия (`has_session_cookie`) имеет приоритет над гостевой, а
  `login_and_save()` не засчитывает появление фоновых гостевых/телеметрийных
  cookie за завершённый вход.
- **Исправлено в `--status`:** флаг `--status` больше не запускает лестницу
  самовосстановления и браузер Playwright при проверке отклонённой сессии — он
  делает ровно один проверочный запрос, выводит вердикт (и подсказку про
  `pip install -e ".[impersonate]"`, если отсутствует `curl_cffi` при ответе
  Cloudflare) и завершает работу с кодом `2`.
- **Исправлено:** когда `AutoSessionManager` использует интерактивный
  `ChallengeWaitSolver` (`solve it in the browser window`), браузер теперь
  открывается с видимым окном (`headless=False`), а не в невидимом headless-режиме.
- **Исправлено в `--diagnose`:** короткие подсказки `sid` / `sess` сопоставляются
  по границам токенов (поэтому `sidebar_state` больше не помечается звёздочкой как
  cookie сессии), а в шапку отчёта добавлена строка `impersonation` со статусом
  `curl_cffi` + `httpx_curl_cffi`.

### Firefox 136+: миллисекундный `expiry`, `recovery.jsonlz4` и живой WAL

- **Исправлено:** начиная со схемы БД 16 (Firefox 136+), `moz_cookies.expiry`
  хранится в **миллисекундах** (`~1.8e12`), а не в секундах (`~1.8e9`) или
  микросекундах (`~1.8e15`), и `rookiepy` возвращает это поле без пересчёта.
  Деление значений `> 1e12` на `1_000_000` превращало все постоянные cookie
  современного Firefox в январь 1970 года (`~1.8e6` с) и отбрасывало их как
  просроченные — в результате `--diagnose` показывал `matching cookies: 0 (12
  expired skipped)`, хотя сессия была живой. Теперь `_expiry_seconds()` различает
  секунды, миллисекунды, микросекунды и наносекунды.
- **Исправлено:** сессионные cookie Firefox (без `Expires`/`Max-Age`) хранятся не
  в `cookies.sqlite`, а в `sessionstore-backups/recovery.jsonlz4` (при открытом
  браузере) и `sessionstore.jsonlz4` / `sessionstore.js` (после закрытия).
  Встроенный читатель и `--diagnose` теперь распаковывают `mozLz40` средствами
  стандартной библиотеки (с откатом на `recovery.baklz4`), поэтому отчёт по
  профилю, счётчик cookie при выборе профиля и `load_cookies()` видят одни и те
  же cookie даже без `rookiepy`.
- **Исправлено:** `rookiepy.firefox()` открывает `cookies.sqlite` с параметром
  `?mode=ro&immutable=1` (SQLite при этом полностью игнорирует `cookies.sqlite-wal`),
  не знает про `--profile-root` / `ARENA_FIREFOX_ROOT` и при явном `--profile`
  на не-дефолтный профиль всё равно читал дефолтный (`candidates[0]` совпадал с
  единственным выбранным кандидатом). Во всех трёх случаях теперь используется
  снимковый читатель с воспроизведением `-wal` и `recovery.jsonlz4`, а записи
  `rookiepy` дополнительно проверяются по целевым доменам (у `rookiepy` в SQL
  используется подстрочный `LIKE '%domain%'`).
- **Исправлено в `--diagnose`:** успешное чтение больше не добавляется в секцию
  `warnings` с маркером `! session read successfully` (из-за чего ветка
  `none -- the session was found and read` никогда не выполнялась, а при пустом
  SQLite и живом `sessionstore` отчёт противоречил сам себе); старые просроченные
  cookie рядом с живым сессионным токеном учитываются в `(N expired skipped)`, не
  объявляя рабочую сессию устаревшей; форматирование дат до 9999 года больше не
  упирается в ограничение `_gmtime64_s` на Windows.

### Firefox: читается тот профиль, где реально лежит сессия (+ `--diagnose`)

- **Исправлено:** профиль выбирался по `profiles.ini` — секция `[Install...]` →
  `Default`, затем профиль с `Default=1`, затем `*.default-release`. На машине с
  несколькими профилями (рабочий, сделанный через `about:profiles`, оставшийся от
  прошлой установки) это регулярно **не** тот профиль, где выполнен вход: менеджер
  возвращал пустой `dict`, а `auto_client()` сообщал «сессия не найдена», хотя
  cookie лежали в соседнем каталоге. Теперь собираются все профили всех каталогов,
  и используется тот, в котором есть cookie для целевых доменов; порядок из
  `profiles.ini` сохранён как порядок предпочтения, поэтому при отсутствии cookie
  везде выбирается он (и `--explain` честно показывает `0 cookies`). Переключение
  печатается в stderr: «using Firefox profile … (it holds the cookies; … does not)».
- **Исправлено:** `rookiepy.firefox()` читает только профиль по умолчанию. Если
  выбран другой профиль, `rookiepy` больше не спрашивают — иначе он вернул бы
  cookie чужого профиля, которые выглядят настоящими. `rookiepy` остаётся первым
  путём для профиля по умолчанию, как и раньше.
- **Новые каталоги профилей:** кроме обычного для ОС, на Linux ищутся
  `~/snap/firefox/common/.mozilla/firefox`, `~/.var/app/org.mozilla.firefox/.mozilla/firefox`
  и `~/snap/firefox/current/.mozilla/firefox`. На Ubuntu со snap-сборкой Firefox
  (и на Flatpak) `~/.mozilla/firefox` не существует, поэтому поиск всегда
  заканчивался «профиль не найден». Новые переменные `ARENA_FIREFOX_ROOT` (каталог
  профилей или путь к `profiles.ini`) и `ARENA_FIREFOX_PROFILE` (имя или абсолютный
  путь), CLI-флаги `--profile-root` / `--profile`; имя профиля ищется и внутри
  `<root>/Profiles`.
- **Исправлено:** срок действия cookie приводится к секундам. `moz_cookies.expiry`
  в старых профилях — микросекунды, а сравнивался он с `time.time()`; теперь
  `_expiry_seconds()` понимает оба варианта, ISO-строки и `0` = сессионная cookie,
  просроченные отбрасываются в Python (а не SQL-условием, зависящим от единиц).
  Записи `cookie_records()` всегда отдают секунды.
- **Исправлено:** контейнерные каталоги (`Profiles`, `Crash Reports`) больше не
  считаются профилями; сообщение об ошибке перечисляет все каталоги, которые
  просматривались, а не один; сообщение о неудачном чтении больше не начинается с
  безобидного «rookiepy не установлен».
- **`--diagnose` (новое):** отчёт о профилях, безопасный для пересылки —
  значения cookie не печатаются никогда, вместо них длина и первые 8 hex SHA-256,
  плюс хост, имя, путь, `Secure`/`HttpOnly`/`SameSite`, срок действия, число строк
  в `cookies.sqlite`, `journal_mode`, выбранный профиль с причиной выбора и
  предупреждения (профиль пуст; cookie просрочены; cookie лежат на другом хосте,
  включая поддомены — тогда нужен `--base-url`; нет «сессионного» имени; каталог
  профилей не найден). `--diagnose --json` — та же структура в JSON.
  Реализация — `arena_api.auth.diagnostics` (`collect_firefox_report`,
  `format_firefox_report`, `report_as_json`), доступна и из Python.
- **`--status`** печатает имена найденных cookie (без значений), `--explain` —
  строку на каждый профиль и строку `Firefox selected`.
- Тесты: `tests/test_firefox_profiles.py` (выбор по содержимому, несколько
  профилей и каталогов, snap, переменные окружения, обход `rookiepy`, единицы
  срока действия, контейнерные каталоги) и `tests/test_diagnostics.py`
  (значение cookie не попадает ни в текст, ни в JSON; предупреждения о просрочке,
  чужом хосте, поддомене, пустом профиле; повреждённая база не ломает отчёт).

### Отпечаток браузера, а не только его cookie: `impersonate`

- Новая причина `ChallengeRequiredError` при формально верной сессии: `cf_clearance`
  и родственные cookie привязаны не только к IP и User-Agent, но и к отпечатку
  соединения (TLS ClientHello + настройки HTTP/2), а у httpx он свой, «питоновский».
  Сессия, аккуратно перенесённая из Firefox, из-за одного этого может получить
  страницу проверки — именно то, что видно в `example_firefox.py` после успешного
  чтения профиля (`arena-auth-prod-v1.0`, `cf_clearance`, `__cf_bm` читаются, а
  запрос к `/config` отбит челленджем).
- `arena_api.transport` умеет отдавать запросы через `curl_cffi` с профилем
  браузера: `ArenaTransport(impersonate="firefox")` строит
  `httpx_curl_cffi.CurlTransport` (async — `AsyncCurlTransport`), не меняя ни
  одного внешнего API: httpx-клиент, SSE-парсер, ретраи и обновление сессии
  работают как раньше. Зависимость ленивая, extra — `[impersonate]`
  (`curl-cffi` + `httpx-curl-cffi`), он же добавлен в `[auto]`.
- Выбор профиля: `impersonate=None` (по умолчанию) следует за источником сессии —
  Firefox-менеджер даёт `firefox`, `BrowserSessionManager` передаёт своё поле
  `impersonate` (его заполняет `arena_api.auto` по найденному браузеру); `False`
  выключает, строка (`"firefox147"`, `"chrome"`) задаёт явно. Если extra не
  установлен, производное значение молча остаётся выключенным, а явное — падает с
  подсказкой `pip install 'arena-api[impersonate]'`; `impersonate=` вместе с
  `http_transport=` — ошибка (impersonation и есть транспорт).
- `auto_client()` / `python -m arena_api` включают это сами: `AutoOptions.impersonate
  = "auto"`, CLI-флаг `--impersonate auto|off|chrome|firefox|…`, строка
  `fingerprint` в `--explain`, уведомление в stderr о выбранном профиле.
  Отображение источников: Firefox → `firefox`; Chrome/Chromium/Brave/Vivaldi/Opera
  → `chrome`; `state/cookies.json`, `ARENA_COOKIE`, `cookies=` → `chrome`
  (заголовки в этих путях и так Chromium-shaped); неизвестный источник — ничего.
- Валидация сессии (`BrowserSessionManager`) использует тот же профиль, что и
  клиент: проба и рабочие запросы больше не идут разными стеками.
- Тесты: `tests/test_impersonate.py` — политика выбора профиля, наличие/отсутствие
  зависимости, сборка sync/async транспорта (записывающий двойник), взаимоисключение
  с `http_transport`, обвязка bootstrap через менеджер, CLI-флаг, а также проверки
  на **реальном сокете**: запрос через curl-транспорт сохраняет наши заголовки и
  cookie, а SSE приходит инкрементально, а не одним куском. CI ставит
  extra `[impersonate]` и гоняет их на всех платформах.
- README: раздел «Отпечаток вместо „нейтрального“ клиента» с таблицей выбора;
  `example_firefox.py` печатает, какой отпечаток ушёл на сервер.

### `--login` в настоящем браузере: `--channel chrome`

- `AutoOptions.channel` + флаг CLI `--channel chrome|msedge`: окно входа
  запускается в установленном браузере, а не во встроенном Chromium. Это
  единственный способ войти в аккаунт, который авторизуется **через Google**:
  Google отклоняет вход из анонимной сборки Playwright («этот браузер или
  приложение может быть небезопасным»), а установленный Chrome принимает.
  Раньше этот путь был доступен только из Python (`login_and_save(channel=...)`),
  CLI его не умел.
- Подсказка при неудачном запуске окна различает случаи: без `--channel` —
  «`playwright install chromium`», с `--channel` — «поставьте Google Chrome либо
  уберите `--channel`», потому что скачивание встроенной сборки такой запуск не
  починит.
- README: раздел «Если Google не даёт войти» — три выхода, включая
  рекомендуемый: войти своим обычным браузером и дать библиотеке прочитать его
  cookie (`auto_client()`, профиль Firefox, `rookiepy` для Chrome/Edge/…), вообще
  не используя Playwright.
- Тесты: `channel` в `AutoOptions`/CLI/override и текст подсказки
  (`tests/test_auto.py`).

### `--hide-automation`: окно входа перестаёт представляться роботом

- `login_environment_options(hide_automation=True)` (и `--hide-automation` в CLI,
  `AutoOptions.hide_automation`) убирает из окна `--login` то, по чему Google
  отличает управляемый браузер: `--enable-automation` уходит в
  `ignore_default_args`, добавляется `--disable-blink-features=AutomationControlled`,
  а на страницу ставится init-скрипт `HIDE_WEBDRIVER_SCRIPT`, снимающий
  `navigator.webdriver` (удаление из прототипа, с `defineProperty` для сборок,
  где `delete` запрещён). Пара `--channel chrome --hide-automation` — рабочая
  комбинация для аккаунта, который входит **через Google**.
- Новое поле `BrowserEnvironmentOptions.extra_init_scripts` — init-скрипты,
  которые ставятся на каждую страницу из `new_page()` **до** первой навигации
  (маска ставится только так: скрипт, добавленный после `goto`, уже опоздал).
  Явные `ignore_default_args`/`launch_args`/`extra_init_scripts`, переданные в
  `login_environment_options`, не затираются, а дополняются.
- Маскировка остаётся opt-in и не проникает в обычный путь: `build_init_script`
  по-прежнему не содержит ни одного стелс-маркера (это стережёт отдельный тест),
  `hide_automation=False` по умолчанию, а при явном `environment_options=`
  вариант вызывающего используется как есть.
- `HIDE_WEBDRIVER_SCRIPT` экспортируется из `arena_api.auth`; заодно убраны
  дубликаты `TOOLKIT_PACKAGE`/`inspect_page` в его `__all__` и добавлен тест
  гигиены (`arena_api.auth` как и верхний уровень: всё импортированное
  объявлено, ничего не объявлено дважды).

### Тесты

- `test_a_saved_result_names_the_file` больше не сравнивает вывод `describe()` с
  POSIX-литералом: `LoginResult.describe()` печатает путь платформо-нативно, и на
  `windows-latest` тот же `Path('state/cookies.json')` читается как

## 0.4.0

### Вход руками один раз: `arena-api --login`

- `arena_api/auth/login.py`: `login_and_save()` / `alogin_and_save()` открывают
  **headed** Chromium с настройками обычного браузера (`identify_automation=False`,
  без детерминизма тестов), ждут, пока вы войдёте, и пишут Playwright
  `storage_state` в `state/cookies.json` — тот самый путь, который
  `auto_client()` ищет в первую очередь. Учётные данные через библиотеку не
  проходят; при желании форму заполняет ваш `LoginFlow`.
- Успех определяется сравнением cookie до и после: раунд засчитывается, когда для
  доменов сайта появились новые cookie, поэтому знать имя сессионного cookie не
  нужно. Файл пишется с правами `0600`, `state/` добавлен в `.gitignore`, а
  «пустое» состояние никогда не перезаписывает рабочую сессию (тогда
  `saved=False`, файл не тронут).
- Существующий `cookies.json` по умолчанию используется как посев контекста
  (`reuse_existing`), чтобы не входить заново; `fresh=True` — войти под другим
  аккаунтом. Отмена (Ctrl-C / закрытый stdin) останавливает ожидание, но всё
  равно возвращает то, что браузер уже накопил.
- `arena_api.auto.interactive_login()` + `LoginOutcome`: тот же вход из кода, с
  последующей проверкой сохранённого файла запросом к `/config`. Проверка
  намеренно не лечит сессию сама (`interactive=False`, `verify=False`) —
  иначе «лекарством» от отказа оказался бы ещё один вход.
- CLI: `--login` (коды возврата 0/1/2), `--fresh`, `--headless`,
  `--login-rounds`, а `--storage` теперь описывает и куда сессия сохраняется.
  `--login --models` входит и сразу выполняет задачу с новой сессией.

### Другие типы капчи, а не только reCAPTCHA

- `ChallengeKind.DATADOME`: DataDome определяется по фреймам
  `captcha-delivery.com`/`geo.captcha-delivery.com`, заголовкам
  `x-datadome`/`x-datadome-cid` и селекторам `DATADOME_SELECTORS` — и в быстром
  HTTP-пути, и в браузере.
- `ChallengeWaitSolver` закрывает виды, у которых токена не существует:
  Turnstile и managed Cloudflare ожидаются (страница пересканивается, пока
  challenge не исчезнет), hCaptcha/DataDome/неизвестный экран передаются
  человеку в headed-окне (`interactive=True` — подсказка и продление ожидания по
  Enter). Результат — `CaptchaAttempt(cleared=True, token=None)`; успех, как и
  прежде, определяет `ChallengeHandler` своим пересканированием.
- Enter в интерактивном ожидании спрашивается в рабочем потоке
  (`asyncio.to_thread`): блокировка event loop остановила бы и Playwright, то
  есть как раз ту страницу, которая должна пройти проверку.
- `CompositeSolver` распределяет виды между солверами (первый поддержавший
  выигрывает), `solver_for()`/`describe_solver()` — публичные помощники.
- `DirectVerificationToken` (`verification_token="auto"`) больше не может тихо
  вернуть пустой assertion: композитный солвер разворачивается до токен-моста
  (`_token_solver`), солвер, который reCAPTCHA не поддерживает (ожидание на
  машине без `playwright-recaptcha`), отклоняется с подсказкой, а пустой токен
  после «успешного» снятия экрана превращается в `AuthenticationError`.
- `resolve_solver()` собирает композит автоматически: токен-мост (если
  зависимости на месте) + ожидание. Так как ожиданию нужен только Playwright,
  `solve_captchas="auto"` больше не «ничего» на машине без
  `playwright-recaptcha`. Новые поля `AutoOptions`: `wait_out_challenges=True`,
  `challenge_wait_timeout=30.0`; флаги `--no-wait`, `--wait-timeout`; строка
  `--explain` показывает, какой солвер действительно будет работать.
- `inspect_page_sync()` — синхронный двойник инспектора страницы (те же сигналы,
  классификация и диагностика на диске); общий код вынесен в `_frame_signals`,
  `_scan_signals`, `_capture_target`/`_finish_capture`.
- Исправлена классификация по селектору: `.h-captcha` (документированный класс
  виджета из `HCAPTCHA_SELECTORS`) не содержал подстроки `hcaptcha` и потому
  попадал в `UNKNOWN`. Сравнение теперь игнорирует пунктуацию.
- `REMEDIATION_TEMPLATE` подсказывает не только инфраструктурные решения, но и
  то, что экран можно подождать или решить руками там, где это разрешено.
